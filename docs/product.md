# 제품 개요

## 대상과 배포
- 팀이 스스로 호스팅하는 비공개 도구다. 공개 배포나 SaaS로 내놓지 않는다.
- 팀원 여러 명이 데몬 하나에 접속한다. 따라서 다중 사용자를 전제로 설계한다.
  - paseo는 소유자 한 명과 비밀번호 하나를 전제로 만들어졌다. 사용자·권한 계층은 이 제품이 새로 추가해야 한다.

## 사용자와 권한
- 사용자 등급은 관리자와 일반 두 가지다.
- 관리자만 할 수 있는 일:
  - 폴더와 에이전트 설정
  - 사용자 관리
  - 디렉토리별 접근 허용 목록 관리
- 일반 사용자는 접근을 허용받은 디렉토리에서만 일한다. 그 안에서는 보기, 지시, 도구 승인을 모두 할 수 있다.
- 아직은 보기, 지시, 승인 권한을 따로 나누지 않는다. 필요해지면 기존 데이터를 깨지 않는 방식으로 확장한다.
- 로그인:
  - 계정은 관리자가 발급한다. 아이디와 비밀번호로 로그인한다.
  - SSO는 쓰지 않는다.
- 메신저 계정 연결:
  - 팀원이 웹에서 일회용 페어링 코드를 발급받는다.
  - 그 코드를 텔레그램/슬랙 봇에게 DM으로 보낸다.
  - 그러면 메신저 계정이 그 팀원의 monday 계정에 연결된다.
  - 연결된 계정만 봇을 쓸 수 있다. 권한 검사는 연결된 monday 계정을 기준으로 한다.
- 메신저와 디렉토리의 연결:
  - 관리자가 슬랙 채널이나 텔레그램 그룹을 디렉토리 하나에 묶는다.
  - 묶인 채널 안에서 스레드 하나(텔레그램은 포럼 토픽 하나)가 대화 하나가 된다.
  - 봇과의 DM에서는 `/dir` 명령으로 디렉토리를 고른 뒤 개인 대화를 연다.
  - 채널 멤버라도 그 디렉토리에 접근 권한이 없으면 봇은 요청을 거부한다.
- 도구 승인:
  - 승인 요청은 그 대화가 있는 곳에 표시된다. 메신저에서는 스레드 안의 버튼으로, 웹에서는 대화 화면에 뜬다.
  - 디렉토리 접근자라면 누구나 승인하거나 거부할 수 있다.
  - 어떤 작업에 승인을 물을지는 역할의 권한 모드(프로바이더의 기존 모드)가 정한다. 별도의 규칙 엔진은 만들지 않는다.
  - 30분 동안 아무도 응답하지 않으면 거부로 처리한다.
- 메신저 명령:
  - `/new`: 새 대화를 연다.
  - `/stop`: 진행 중인 턴을 멈춘다.
  - `/status`: 오케스트레이터와 서브에이전트의 상태를 보여준다.
  - `/dir`: DM에서 디렉토리를 고른다.
  - `/link`: 페어링 코드로 메신저 계정을 연결한다.
  - 스레드 안에서 명령이 아닌 일반 텍스트는 오케스트레이터에게 전달된다.
  - 승인은 버튼으로만 한다.
  - `/model`, `/undo` 같은 명령은 두지 않는다. 모델은 역할에 고정되어 있고, 폴더를 공유하므로 undo를 하면 다른 대화의 변경까지 되돌릴 위험이 있기 때문이다.
- 알림 (완료, 실패, 승인 대기):
  - 알림은 대화가 시작된 곳으로만 보낸다.
  - 메신저에서 시작한 대화라면 그 스레드에 알림을 올리고, 지시한 사람을 멘션한다.
  - 웹에서 시작한 대화라면 웹 화면 안에만 표시한다.
  - 웹 푸시는 쓰지 않는다. 웹 푸시는 HTTPS가 필요한데, 이 제품은 사설망에서 HTTP로 운영하기 때문이다.
- 감사 로그 (게이트웨이가 기록한다):
  - 기록하는 것:
    - 지시: 누가, 어느 디렉토리와 대화에, 웹과 메신저 중 어디서 했는지
    - 승인과 거부: 무응답으로 거부된 경우도 포함
    - 관리자 변경: 팀 구성, 접근 목록, 프로바이더 항목, 사용자. 변경 전후 값을 남기되 비밀값은 가린다.
    - 로그인, 페어링, 터미널 열기
  - 기록하지 않는 것: 대화 내용(데몬에 이미 있다), 터미널 입력
  - 관리자 화면에서 조회한다.
  - 1년이 지나면 자동으로 삭제한다.
- 예약 실행:
  - paseo의 스케줄 기능을 디렉토리 팀에서 쓸 수 있게 한다.
  - 예약을 만들거나 고치는 것은 관리자만 할 수 있다.
  - 실행 결과는 디렉토리에 묶인 채널에 새 스레드로 올라간다.
  - 실행 중 승인이 필요하면 다른 작업과 같은 규칙이 적용된다. 30분 동안 응답이 없으면 거부된다.

## 프로바이더 계정
- 에이전트는 기본적으로 관리자가 등록한 프로바이더별 조직 API 키로 실행된다.
- 팀원은 원하면 자기 계정을 연결할 수 있다. 방식은 paseo와 같다.
  - 계정은 사용자가 아니라 **프로바이더 항목**에 붙는다.
  - 관리자가 기본 프로바이더를 바탕으로 개인용 항목을 만든다. 예: `claude-<이름>` 항목에 그 사람의 API 키나 로그인 폴더를 지정한다.
  - 에이전트는 자신이 어느 프로바이더 항목으로 실행되는지만 안다.
  - API 키와 구독 로그인 중 어느 것으로 연결해도 된다. 구독 약관을 지킬 책임은 그 계정 주인에게 있다.
- 각 에이전트가 쓸 프로바이더 항목은 관리자가 에이전트 설정에서 정한다. 누가 지시하든 그 에이전트는 정해진 항목으로 실행된다.
- 데몬 호스트 한 사람의 구독 로그인을 팀 전체가 같이 쓰는 것은 금지한다. 약관 위반이다. 근거: [ADR-261109-160746](../.forge/adr/261109-160746-provider-credentials-org-and-personal.md)
- 지원 프로바이더:
  - paseo의 프로바이더 코드는 모두 유지한다.
  - 공식적으로 보증하고 팀 기능(역할, 메신저 승인 등)을 검증하는 대상은 claude와 codex다.
  - 나머지 프로바이더도 동작은 하지만 보증하지 않는다.
- 사용량:
  - 관리자 화면에서 토큰 사용량을 프로바이더 항목별, 디렉토리별, 지시자별로 모아 보여준다.
  - 예산 한도나 차단 기능은 없다. 조직 키의 한도는 각 프로바이더 콘솔에서 건다.

## 핵심 개념
- **디렉토리**는 관리자가 등록하는 작업 단위다.
  - 루트 경로 하나에 대응하며, paseo의 Project에 해당한다.
  - git 저장소가 아닌 폴더도 등록할 수 있다.
  - 에이전트 팀과 접근 허용 목록은 디렉토리에 붙는다.
  - 그 아래에 생기는 worktree도 같은 팀과 같은 권한을 공유한다.
- 에이전트 팀 구성은 데몬 저장소(`~/.monday`)에 저장한다.
  - 디렉토리 안에는 두지 않는다. 에이전트가 자기 팀 구성을 고치지 못하게 하려는 것이다.
  - 편집은 관리자 화면에서만 한다. 근거: [ADR-261109-163314](../.forge/adr/261109-163314-team-config-in-daemon-store.md)
- 한 폴더에 오케스트레이터와 서브에이전트로 이루어진 에이전트 팀을 배치하고 함께 동작시킨다.
- **대화**는 사용자가 일을 시키는 단위다. 웹 세션 하나나 메신저 스레드 하나가 대화 하나에 해당한다.
  - 대화마다 오케스트레이터가 새로 뜬다.
  - 같은 디렉토리에서 여러 대화가 동시에 실행될 수 있다.
  - 모든 대화는 디렉토리의 같은 폴더를 공유한다. worktree로 격리하지 않는다.
  - 단, 에이전트가 판단해서 스스로 worktree를 만드는 것은 허용한다. 그 결과를 본 폴더에 합치는 일은 사용자가 한다.
  - 따라서 두 대화가 같은 파일을 동시에 고치면 한쪽 변경이 사라질 수 있다. 이 위험은 운영으로 피한다. 근거: [ADR-261109-165913](../.forge/adr/261109-165913-shared-directory-no-isolation.md)
- 에이전트 팀은 **오케스트레이터** 하나와 여러 **역할**로 구성된다.
  - 각 역할은 데몬 수준의 에이전트(paseo agent)로 실행된다.
  - 역할 하나는 다음 항목으로 정의한다: 이름, 설명, 프롬프트, 프로바이더 항목, 권한 모드. 오케스트레이터는 설명이 없는 특수 역할이다.
  - 오케스트레이터는 MCP 도구 `spawn_role(역할, 작업)`으로만 서브에이전트를 띄운다.
  - 팀이 있는 디렉토리에서는 paseo의 `create_agent` 도구를 막는다. 역할 정의를 벗어난 에이전트(예: 관리자가 지정하지 않은 프로바이더 항목을 쓰는 에이전트)가 만들어지지 않게 하려는 것이다.
  - 역할마다 다른 프로바이더 항목을 쓸 수 있다.
  - 각 에이전트가 내부적으로 자기 프로바이더의 고유 서브에이전트를 쓰는 것은 막지 않는다.
  - 서브에이전트는 작업 하나를 위해 만들어진다. 부모가 보관 처리되면 함께 보관 처리된다(일회형).
  - 계속 쌓아 둘 지식은 역할 프롬프트나 디렉토리 문서에 기록한다.
- 팀 구성에는 MCP 서버와 env(비밀값 포함)를 정의할 수 있다.
  - 여기에 정의한 것은 팀의 모든 역할에 주입된다.
  - 역할별로는 항목을 추가하거나 빼는 것만 할 수 있다.
  - 비밀값은 에이전트의 env로 들어간다. 그래서 그 디렉토리의 에이전트와, 그 에이전트에게 지시할 수 있는 접근자는 비밀값을 볼 수 있다고 전제한다. 다른 디렉토리로는 새지 않는다. 디렉토리마다 OS 사용자가 따로 있기 때문이다.
- 사용자가 지시하는 경로:
  - 웹: 오케스트레이터에게 지시할 수 있고, 서브에이전트 탭에도 직접 입력할 수 있다.
  - 메신저: 오케스트레이터에게만 지시한다.
- 제어 경로:
  - 웹앱 사용자 화면에 들어가는 기능:
    - 대화: 오케스트레이터, 서브에이전트 탭, 도구 승인
    - 파일 탐색기 (읽기 전용)
    - 터미널 (관리자만 사용 가능. 데몬 호스트의 셸이기 때문이다)
  - 웹앱 사용자 화면에 넣지 않는 기능: diff 보기, 파일 편집
  - 웹앱: 하나의 앱 안에 역할별 메뉴를 둔다. 관리자 메뉴(디렉토리·팀·프로바이더 항목·사용자 관리)는 관리자에게만 보인다. 관리자 기능도 네트워크를 통해 접근할 수 있다.
  - 텔레그램
  - 슬랙

## 범위 밖
- 음성 입력과 출력: 요청에 없었고, 웹과 메신저로 충분히 제어할 수 있다.
- Hermes 기반 구축, Hermes 코드 재사용: Hermes는 Python이다. 설계만 참고한다.
- paseo가 운영하는 relay(`relay.paseo.sh`): 타사 서비스에 의존하게 된다.
- 인터넷 공개 배포(TLS, 공인 도메인, 자체 relay): 사설망을 전제로 한다.
- macOS 네이티브 배포: Mac에서는 Docker Desktop으로 실행한다.
- 여러 머신의 데몬을 게이트웨이 하나로 묶기: 머신마다 따로 설치한다.
- 웹의 diff 보기와 파일 편집
- 사용량 예산 한도와 차단
