# 아키텍처

## 기반
- paseo(Apache-2.0)를 포크해서 쓴다. 신규 기능은 추가 패키지로 얹는다.
  - 근거: [ADR-261109-152306](../.forge/adr/261109-152306-paseo-fork-additive-packages.md)
  - 조사 자료: [research/paseo-hermes.md](research/paseo-hermes.md)
- upstream remote를 유지하고 주기적으로 병합한다.
- paseo 서버(`packages/server`)는 최소한으로만 고치고, 고친 부분은 격리한다.
- 메신저 봇과 관리자 웹은 새 패키지로 만든다.
- 쓰지 않는 paseo 패키지는 파일을 지우지 않는다. 루트 `workspaces`와 빌드에서만 뺀다.
  - 빼는 패키지: `desktop`, `app`, `website`, `expo-two-way-audio`
  - `relay`는 `server`와 `client`가 의존하므로 빌드에 남긴다. 데몬 설정에서 relay 연결만 끈다.
  - 남기는 패키지: `server`, `cli`, `client`, `protocol`, `plugin`, `highlight`, `relay`
- 제품명은 `monday`다. 사용자에게 보이는 것(CLI `monday`, `~/.monday`, 환경변수 접두사, UI)만 바꾼다. 내부 패키지 이름 `@getpaseo/*`는 그대로 둔다 — 근거: [ADR-261109-160355](../.forge/adr/261109-160355-rebrand-user-facing-only.md).
- "Paseo" 이름과 브랜드는 사용자에게 보이는 곳에 쓰지 않는다. 가져온 파일의 LICENSE·저작권 표기는 유지하고, 수정한 파일에는 수정했다고 표시한다.

- 웹앱은 새로 만든다. paseo `packages/app`(Expo)은 개조하지 않는다. 근거: [ADR-261109-171228](../.forge/adr/261109-171228-new-web-app.md)

## 구성 요소
- **데몬**: paseo 서버를 포크한 것이다.
  - localhost에서만 연결을 받는다.
  - 단일 소유자를 전제로 한다.
  - 에이전트, 프로바이더, 디렉토리(Project)를 실행하고 관리한다.
  - 디렉토리별 에이전트 팀은 서버의 새 도메인 개념 "팀"으로 구현한다. 서버 안에서도 별도 모듈로 격리한다. 근거: [ADR-261109-172323](../.forge/adr/261109-172323-team-as-server-concept.md)
- **에이전트 프로세스**: 데몬과 다른 OS 사용자로 실행한다.
  - 데몬의 설정과 키(`~/.monday`)를 읽을 수 없게 하기 위해서다.
  - OS 사용자는 디렉토리마다 하나씩 둔다. 파일 권한으로 디렉토리끼리 격리하기 위해서다.
  - 그래서 데몬은 OS 사용자를 만들기 위해 root(sudo) 권한이 필요하다. 근거: [ADR-261109-171902](../.forge/adr/261109-171902-agent-separate-os-user.md)
- **게이트웨이**: 새로 만드는 서비스다.
  - 사용자, 권한(관리자/일반 + 디렉토리 접근 목록), 감사 로그를 맡는다.
  - 포크 모노레포 안의 새 Node/TS 패키지다.
  - 데이터는 SQLite에 저장한다: 사용자, 비밀번호 해시, 디렉토리 접근 목록, 메신저 계정·채널 바인딩, 페어링 코드, 감사 로그.
  - 데몬과 팀 구성 데이터는 paseo 방식(`~/.monday` 아래 JSON 파일) 그대로 둔다.
  - `@getpaseo/client`로 데몬에 붙는다.
  - 타입은 `@getpaseo/protocol`의 것을 그대로 쓴다.
  - 외부에 노출되는 진입점은 게이트웨이 하나뿐이다.
  - 게이트웨이는 지정한 주소에 HTTP로만 연다.
  - 접근은 사내망, VPN, Tailscale 같은 사설망 안에서만 한다.
  - 인터넷 공개, TLS, relay는 제품 범위에 넣지 않는다.
  - 근거: [ADR-261109-171338](../.forge/adr/261109-171338-auth-gateway-in-front-of-daemon.md)
- **웹앱**: React와 Vite로 만드는 SPA다.
  - 게이트웨이가 정적 파일로 서빙한다.
  - 게이트웨이와만 통신하며, 통신 방식은 WebSocket이다.
- **메신저 봇**(텔레그램/슬랙): 게이트웨이를 거쳐서 동작한다.
  - 바깥으로 나가는 연결만 쓴다. 텔레그램은 롱폴링, 슬랙은 Socket Mode다.
  - 따라서 사설망 밖에서도 메신저로는 제어할 수 있다.
  - 먼저 공통 메신저 어댑터 인터페이스를 정의한다. Hermes의 `BasePlatformAdapter` 설계를 참고해 TS로 새로 작성한다.
  - 텔레그램과 슬랙은 이 인터페이스의 구현체로 만든다. 다른 플랫폼은 나중에 어댑터만 추가하면 된다.

```
웹앱 ──────┐
텔레그램 봇 ├─▶ 게이트웨이(사용자·권한·감사) ─▶ 데몬(localhost, paseo 포크) ─▶ 에이전트들
슬랙 봇 ────┘
```

## 배포
- 한 호스트에 게이트웨이 하나와 데몬 하나를 둔다. 데몬 하나가 여러 디렉토리를 관리한다.
- 여러 머신에서 쓰려면 머신마다 monday를 따로 설치한다. 다른 머신의 데몬들을 게이트웨이 하나로 묶지 않는다.
- 지원 플랫폼은 Linux 서버(systemd로 자동 시작)와 Docker 이미지다.
- macOS 네이티브는 지원하지 않는다. Mac에서는 Docker Desktop으로 실행한다.
- 백업과 복구는 CLI로 한다.
  - `monday backup`: 다음 세 가지를 아카이브 하나로 묶는다.
    - `~/.monday` JSON
    - 게이트웨이 SQLite (온라인 백업 API로 일관성을 유지한다)
    - 디렉토리와 OS 사용자의 매핑
  - `monday restore`: 아카이브를 복구한다. OS 사용자와 파일 소유권도 다시 만든다.
  - 업그레이드하기 전에 자동으로 백업한다.
  - 디렉토리 안의 내용은 백업하지 않는다. git이나 기존 백업으로 관리한다.
  - 아카이브에는 프로바이더 키가 들어 있으므로 민감 자산으로 다룬다.
- Docker 안에서는 호스트의 Claude Code/Codex 로그인을 쓸 수 없다. 구독 로그인으로 연결한 프로바이더 항목은 컨테이너 안에서 따로 로그인해야 한다.
